# 角色引导机制

Innovation-Products_ppt 的多 agent 不是越多越好。默认四个角色已经足够：策划师（含布局蓝图）、视觉设计师、组件管理员、审阅员；讲稿由主 Agent 直接写，不设角色。真正需要补的是“同一个项目目标如何传递给不同角色”。

## 项目级角色引导包

每个多页 PPT 项目都应有 `role-briefs.md`。它不是新 agent，也不是另一份大纲，而是角色进入任务前的项目说明。

它负责回答：

- 这个项目对每个角色最重要的判断是什么？
- 哪些用户反馈已经确认，必须被所有角色遵守？
- 哪些问题是本项目高风险项？
- 每个角色的输出要交给下一环节什么材料？
- 哪些事项不能由该角色越权决定？

## 与其他项目文件的关系

| 文件 | 作用 | 谁主要读取 |
|---|---|---|
| `brief.md` | 任务目标、受众、边界 | 全部角色 |
| `outline.md` | 页面故事线、页序、页面任务 | 策划师（含布局蓝图）、主 Agent 写讲稿时 |
| `DESIGN.md` | 设计系统、颜色、字体、组件风格 | 策划师（含布局蓝图）、视觉设计师、审阅员 |
| `visual-direction.md` | 本项目视觉目标、表达模式、图片/截图策略 | 策划师（含布局蓝图）、视觉设计师、审阅员 |
| `role-briefs.md` | 每个角色如何使用上述信息 | 全部角色 |
| `agent-collaboration.json/md` | 角色是否运行、输出证据和结论 | 主流程、最终关卡 |

## 必须包含的角色

`role-briefs.md` 至少包含这些小节：

- `planner-zh`（含布局蓝图）
- `visual-designer-zh`
- `component-curator-zh`
- `reviewer-zh`

如果某个角色暂时不运行，也要写清“不运行原因”和“由谁覆盖它的检查”。

## 各角色引导重点

### planner-zh

重点不是改文字，而是确保故事线可讲、页面之间有承接、一个概念只有一个称呼。

需要特别说明：

- 本 PPT 的主问题是什么。
- 本 PPT 采用哪一种大叙事框架。内部分享通常先用“大问题 -> 当前环境 -> 目标问题 -> 我们的方案 -> 方案展开 -> 实施与效果”，再按项目调细节。
- 章节之间的递进关系。
- 哪些页是定义、证据、机制、案例、总结或转场。
- 哪些事实不能虚构，需要用户补充或会前核实。

同一个 `planner-zh` 在同一轮内继续把大纲落成布局蓝图，重点是整套 PPT 的节奏、版式差异和蓝图可执行性。

蓝图部分需要特别说明：

- 哪些页需要大字、机制图、截图证据、流程图、图片或表格。
- 哪些页面不能重复使用同一版面结构。
- 每章的视觉节奏应该怎样变化。
- 低保真预览中哪些错乱会影响后续真实页面，不能视为“只是示意”。

### visual-designer-zh

重点是最终画面是否真的被设计过。

需要特别说明：

- 本项目视觉气质。
- 红色、深蓝、灰色和图片的语义。
- 哪些页必须避免“框 + 箭头 + 小字”。
- 哪些页需要真实截图、简单 image2 或外部渲染。

这部分通常引用 `visual-direction.md`，但不要把 `visual-direction.md` 当成新角色。

### component-curator-zh

重点是组件是否按表达关系复用，而不是按当前语义关键词硬套。

需要特别说明：

- 组件选择要受 `layout-blueprint.json` 约束。
- 组件按 `relationPrimitive`、`expressionCapability`、`slots`、`variants` 评估。
- 新图形是新组件、旧组件变体，还是只属于本项目一次性实现。
- 哪些项目特例不能积累到公共组件库。

### reviewer-zh

重点是独立检查，不能帮生产者找借口。

需要特别说明：

- 本项目最容易复发的 P0/P1 问题。
- 哪些设计偏好已经被用户明确确认。
- 动态 QA 之外还要检查哪些本项目特定风险。
- 哪些问题一旦出现必须 `FIX-FIRST`，不能写成“后续精修”。

## 讲稿（不是角色）

`speaker-notes.md` 由**主 agent** 在终版页面之后直接写，不再开独立 subagent、不占 fresh-fork 预算。写的时候仍然覆盖：听众是谁与可能卡住的概念、每章开场/转场/收束口径、哪些页需要口播补充、哪些事实需会前核实、以及哪些机制是"已实现"而非"设计方案"。

## 关卡规则

最终构建前，`tools/verify-agent-collaboration.js` 应检查：

- `role-briefs.md` 存在。
- 必需角色在 `role-briefs.md` 中有对应小节。
- `agent-collaboration.json` 中必需角色有状态、结论、证据或 fallback 原因。

如果没有角色引导包，就不能声称“多 agent 机制已经完整运行”。

## 常见错误

- 只给视觉设计师写引导，其他角色靠默认模板工作。
- 把 `visual-direction.md` 当成新 agent。
- `role-briefs.md` 复制当前 PPT 大纲，却没有说明各角色分别要判断什么。
- agent 输出只写“PASS”，没有说明依据哪个项目约束判断。
- reviewer 把明显错误写成“后续精修”。
