# 视觉构成与效果验证

本文件用于判断一页 PPT 是否真的被设计过，而不仅仅是没有报错、没有明显重叠、符合模板。

## 什么时候读取

在以下阶段读取：

- 创建或修改 `visual-direction.md`。
- 设计蓝图和低保真预览。
- 制作 anchor sample。
- 在 PPT 组件、外部渲染、真实图片、image2 生成图之间做选择。
- 修复“空、挤、死板、AI 味、过度卡片化、缺少设计感”的页面。
- 全量渲染后做视觉设计师 agent 复核。

早期 brief 抽取阶段不需要读取，除非用户明确在讨论视觉风格。

## 视觉导向不是 QA

QA 负责判断页面是否有问题：重叠、溢出、歪线、字号太小、颜色无意义。

视觉导向负责定义页面应该变得更好看、更有表达力的方向：

- 整套 PPT 的视觉气质是什么？
- 哪些页面应该大字表达，哪些页面应该机制图表达？
- 哪些页面需要真实截图或 image2？
- 哪些页面必须避免“框 + 箭头 + 小字”的机械感？
- 缩略图连看时，整套 PPT 是否有叙事节奏？

因此，进入蓝图或样页前，应先有项目级 `visual-direction.md`。渲染后如果“没错但不好看”，应先回到 `visual-direction.md`，而不是只继续调坐标。

## 视觉导向不是新 Agent

`visual-direction.md` 是项目级视觉 brief，不是一个额外的子 agent。

- 主流程用它约束蓝图、样页和页面生产。
- `visual-designer-zh` 用它做视觉复核和美感判断。
- `layout-architect-zh` 可以用它检查整套 PPT 的节奏和版式差异。
- `reviewer-zh` 可以用它补充“没错但不好看”的判断依据。

不要新增 `visual-direction`、`visual-guide`、`art-director` 之类的独立 agent，除非用户明确要求重构 agent 体系。默认做法是把视觉导向并入现有视觉设计师角色和主流程门禁。

## 视觉来源选择逻辑

从页面关系出发选择视觉来源。

| 页面关系 | 优先视觉来源 |
|---|---|
| 顺序 / 流程 | 可编辑 PPT 流程图或时间线 |
| 层级 / 系统 | 可编辑 PPT 架构图、中心发散图、树形图 |
| 对比 / 选项 | 左右对照、矩阵、before/after |
| 量化证据 | PPT 指标卡 + 图表；数据形态复杂时用 ECharts |
| 密集数据模式 | ECharts / 外部渲染 + PPT 注释层 |
| 真实产品 / 场景 | 真实图片优先，缺素材时用 image2，空间关系复杂时用 3D/外部渲染 |
| 空间 / 三维机制 | Three.js / Spline / image2 简化示意 + PPT 标注 |
| 地理 / 路线 | 地图渲染 + PPT 解释层 |
| 封面 / 氛围 | 真实图片或 image2，文字极少，裁剪要强 |
| 文件 / 目录 / Agent / QA | 真实截图或局部截图 + 解释锚点 |

## 颜色语义门禁

页面通过前，每个非中性色都必须有明确任务。

红色或强调色允许的任务：

- 当前焦点
- 问题 / 风险 / 失败
- 当前步骤
- 决策 / 例外
- before/after 对比中的变化侧
- Gate 或关键变化

如果说不出颜色任务，就降级为深蓝、灰色或浅底。不要让红色变成“看起来重要”的装饰描边。同级元素应使用同一种结构色，除非页面明确表达不同类别。

## 图片机会门禁

每个章节都要主动检查是否至少有一页更适合使用真实图片、截图、外部渲染或简单 image2。

图片适合承担：

- 场景真实感
- 产品或环境证据
- 空间 / 三维理解
- 简单隐喻，降低图形复杂度
- 封面、转场、封底的情绪锚点

图片不适合承担：

- 精确流程
- 多节点架构
- 数据关系
- UI 截图替代
- 有来源要求的事实证据

image2 生成图必须简单、无文字、无复杂流程，并且服务页面主逻辑。不要用 image2 画密集流程、技术架构、表格、小字标签或事实证据。

## 组合规则

- PPT 可编辑组件负责结构和观点。
- 外部渲染负责 PPT 图形难以表达的复杂视觉。
- image2 负责场景、氛围、概念隐喻和缺失素材。
- 真实截图负责证明真实文件、真实流程和真实系统存在。
- 外部渲染源、图片提示词或截图来源应保存在工作目录。
- 当生成图或占位图可能被误解成事实证据时，必须标注边界。

## 设计过的页面应满足

一页通过视觉构成检查，需要满足：

- 有一个明确焦点。
- 标题、结论和图形表达同一个意思。
- 文字和图形互相解释，而不是互相竞争。
- 留白与焦点成比例，且有意图。
- 有主、次、辅三层视觉层级。
- 图标、图片、图表承担信息，不只是装饰。
- 组件选择匹配页面关系。
- 不把“标题 + 段落 + 卡片”当成默认模式。
- 缩略图状态下也能看出这一页的视觉任务。

## 留白检查

好的留白：

- 承托大字、数字、图片或结论。
- 拉开焦点和辅助证据的层级。
- 有对齐、规则线或组件节奏。

坏的留白：

- 让小字孤零零漂在页面上。
- 让卡片显得稀疏。
- 只是因为内容没填满。
- 让主体无意偏上、偏下或偏边。

## 混合素材 QA

当一页混合 PPT 组件、外部渲染、截图和图片时，检查：

- [ ] 所有视觉来源共用同一版面网格。
- [ ] 外部图片/渲染有明确存在理由。
- [ ] PPT 可编辑层解释了图片/渲染层。
- [ ] 标注、说明和风险边界靠近对应视觉。
- [ ] 页面不像几个截图随手拼贴。
- [ ] 字体、颜色、线宽、留白和主题一致。

## 渲染后效果验证

最终 PPT 必须用渲染图说话。每次输出预览图或成品页后，按五层看：

1. **远看**：contact sheet 缩略图中，是否能看出每页不同的视觉任务？
2. **中看**：单页 50% 缩放时，主体是否居中、焦点是否明确、颜色是否有意义？
3. **近看**：文字是否可读，是否有重叠、溢出、压框、歪线？
4. **连看**：相邻页面是否有故事节奏，而不是重复一个版式？
5. **讲看**：假设现场汇报，图形是否帮助听众理解，而不是需要解释“这个图想表达什么”？

## 自检

- [ ] 视觉来源由页面关系决定，而不是随手套组件。
- [ ] 页面有明确焦点。
- [ ] 文字量适合当前空间。
- [ ] 留白是设计出来的，不是内容没填满。
- [ ] 图片、图标、图表有信息价值。
- [ ] 生成图没有被当成事实证据。
- [ ] contact sheet 缩略图下仍然有节奏和差异。
- [ ] 不存在“没有报错但明显不好看”的页面被直接交付。
