# 叙事框架

本文件用于把内部分享、方法论介绍、项目复盘、方案汇报等 PPT 先组织成能讲的故事，再进入页面拆解和视觉设计。

## 核心原则

叙事框架应该抽象到“多数内部分享都能复用”的层级，不要把某一个项目的页序、术语和案例固化为通用模板。

通用叙事只回答：

- 听众为什么要听？
- 当前环境为什么让这个问题变重要？
- 我们到底要解决哪个问题？
- 我们提出什么方案？
- 方案如何展开、如何运行、为什么可信？
- 接下来怎么做，预计带来什么变化？

具体项目再决定每一段需要几页、用什么案例、是否插入转场和截图。

## 内部分享六段式

默认从下面六段开始，再根据 deck type 调整：

| 段落 | 叙事任务 | 典型页面任务 | 常见表达 |
|---|---|---|---|
| 1. 大问题 | 把听众带进一个更大的问题或现象 | 痛点、反差、效率问题、失败模式 | 大字张力、问题发散、before/after |
| 2. 当前环境 | 说明为什么现在值得讨论 | 行业动作、技术演进、内外部趋势、案例证据 | 时间线、案例证据、趋势地图 |
| 3. 目标问题 | 从大环境收敛到本团队/本项目真正要解决的问题 | 问题定义、边界、成功标准、约束 | 概念边界、问题地图、诊断图 |
| 4. 我们的方案 | 给出核心方案和整体框架 | 总架构、方法论、方案总览、能力层 | 中心框架、架构图、脑图 |
| 5. 方案展开 | 拆解方案如何运行 | 流程、机制、工具、角色、QA、组件、数据 | 机制图、流程图、截图证据、组件树 |
| 6. 实施与效果 | 说明如何落地、风险和预期收益 | 实施计划、协作机制、收益、迁移、下一步 | 路线图、收益海报、迁移图、行动清单 |

## 使用方式

在 `brief.md` 阶段先选 deck type，在 `outline.md` 阶段把页面归入六段之一。

每页至少说明：

- 属于哪一段。
- 这一页在该段里承担什么任务。
- 它如何承接上一页、引出下一页。
- 是在放大问题、提供证据、定义边界、提出方案、解释机制，还是推动行动。

## 何时调整

这个六段式不是死模板。可以按场景调整：

- **管理汇报**：大问题 -> 业务影响 -> 方案选择 -> 资源请求 -> 计划风险 -> 决策事项。
- **项目复盘**：目标 -> 结果 -> 偏差 -> 原因 -> 经验 -> 后续行动。
- **产品介绍**：场景痛点 -> 市场/客户背景 -> 产品定位 -> 能力展开 -> 证据案例 -> 交付路径。
- **培训材料**：学习目标 -> 背景概念 -> 核心方法 -> 操作步骤 -> 练习检查 -> 总结迁移。

调整时保留“从为什么到怎么做，再到接下来”的大逻辑，不要直接套某个具体项目的细页序。

## 常见错误

- 一上来讲方案，没有先让听众理解为什么要关心。
- 外部环境讲太多，没有收敛到本团队要解决的问题。
- 方案总览和机制拆解混在一页，听众不知道先看整体还是看细节。
- 每页都在解释概念，但没有实施计划、风险和预期效果。
- 把某个项目的章节名当成通用叙事骨架。

## 输出建议

在 `outline.md` 的 storyline 后增加一张叙事映射表：

```markdown
| Narrative stage | Pages | Job | Key question | Handoff |
|---|---|---|---|---|
| 大问题 | p02-p03 | 让听众看到现象和矛盾 | 为什么这件事值得讲？ | 引出当前环境 |
| 当前环境 | p04-p06 | 用趋势和案例说明时机 | 为什么现在要解决？ | 收敛到目标问题 |
| 目标问题 | p07-p08 | 定义本项目要解决什么 | 我们到底解决哪类问题？ | 引出方案 |
| 我们的方案 | p09-p10 | 给出总框架 | 我们的办法是什么？ | 进入机制拆解 |
| 方案展开 | p11-p20 | 解释方案如何运行 | 它如何稳定工作？ | 引出落地协作 |
| 实施与效果 | p21-p27 | 说明落地、迁移和收益 | 接下来怎么做，有什么效果？ | 收束 |
```
