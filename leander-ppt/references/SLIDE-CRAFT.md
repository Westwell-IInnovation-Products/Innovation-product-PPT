## 何时读

每次创建标杆样张、或实现一批终版幻灯片时,都读本文件。

做全量生产或反馈修复时,还要读 `PRODUCTION.md`。它定义如何隔离页面、批次和章节。

## 这是 PPT,不是文字摘要

一张好的 PPT 页让受众看见关系、机制、对比或结论。一张由标题 + 段落 + 若干文字卡片组成的页,通常不够。

每张内容页都需要一个真实的视觉解释:

- 流程:节点、箭头、检查点、交接。
- 对比:前/后、选项 A/B、竞品、来源/目标。
- 时间线:阶段、里程碑、成熟路径。
- 矩阵:两轴、象限、优先级图。
- 分层架构:栈、平台、依赖、数据流。
- 证据板:数字、来源标签、提醒。
- Dashboard mockup:指标、状态、面板。
- 图片主导页:真实产品、现场、截图,或带清晰说明的生成占位。
- 大字 + 卡片矩阵:一侧设计留白,另一侧密集的支撑卡片。
- 四列机制:等宽列,含编号、标题、图标/图示和结论。

## 做页决策树

画一页之前,先回答这五个问题:

1. 受众应该记住的那一句话是什么?
2. 必须被看见的关系是什么:顺序、层级、对比、因果、证据,还是 system map?
3. 有什么可以从文字里去掉、转成形状、图标、数字、轴或图片?
4. 这是一张设计留白页,还是一张满内容页?
5. 数据边界是什么:已达成、计划中、估算、公开引用,还是未知?

然后再选页面形态。

做修复或全量生产时,还要应用 `PAGE-DESIGN-METHOD.md`:信息优先、关系其次、路线第三、画之前先确认产物真实性、PASS 之前做几何/字号 QA。

| 关系 | 优先 |
|---|---|
| 顺序 / 流程 | 带箭头的横向或环形流 |
| 系统架构(由什么组成) | `archLayered`(Type A):自上而下的分层带 + 模块行 |
| 场景架构(如何协作) | `archDualEngine`(Type B):双核 ✕ + 两翼 + AI 基座 |
| 层级 / 组织 / 分解 | `orgTree`(2 层树 + 孙级 chip) |
| 网络 / 部署拓扑 | `topology`(云-边-端 节点 + 连线) |
| 地理 / 现场覆盖 | `coverageMap`(区域 + 枢纽 + 标绘现场 + 列表) |
| 竖向里程碑时间线 | `timelineVertical`(轴 + 带日期卡片) |
| 编号叙事要点 | `numberedList`(大序号 + 标题 + 描述) |
| 2×2 定位 | `quadrantMatrix`(轴 + 象限 + 标绘点) |
| 优先级 / 重要性分层 | `priorityPyramid`(顶端 = 最重要) |
| 转化 / 变窄 | `funnel`(变窄的带 + 数值) |
| 百分比结果 | `ringStats`(环 + 居中 %) |
| A vs B 决策 | `twoOptionCompare`(两列 + VS + 推荐) |
| 图片 / 截图展示 | `imageGallery`(带框单元 + 说明) |
| 带批注的截图 / 图示 | `annotatedDiagram`(图片 + 编号标记 + 图例) |
| 关键陈述 / 证言 | `quoteHighlight`(大号居中引言) |
| 排期 / 项目计划 | `gantt`(任务 × 周期 + 条 + 里程碑) |
| 基于角色的流程 | `swimlaneProcess`(角色泳道 × 阶段列) |
| 价值 / 流程链 | `valueChain`(重叠 chevron) |
| 贡献 / 价值桥 | `waterfall`(起点 + 增量 + 终点) |
| 强度矩阵(风险/优先级) | `heatmap`(着色单元 + 图例) |
| 多维能力对比 | `radar`(原生图表,marker 样式) |
| 集合重叠 / 交集 | `venn`(半透明圆) |
| 随时间的趋势 | `lineChart`(原生) |
| 类别对比 | `barChart`(原生) |
| 构成 / 占比 | `pieBreakdown`(原生 doughnut + 列表) |
| 四个并列价值 | 四列机制 |
| 并列能力(5-6 个) | `featureGrid`(图标特性卡) |
| 三个产品 / 支柱 | `pillarTrio`(图标圆 + 名称 + 描述 + 子要点) |
| 双面权衡 | 拆分对比或前后 |
| 选项 / 竞品对比 | `capabilityMatrix`(表格:✓ / 分级点 / 文字,焦点列) |
| 分层部署(云-边-端 / 平台层) | `tierStack`(层标签轨 + 组件 chip) |
| 分类枚举(需求 / 痛点 / 能力) | `bulletColumns`(类别列 + 结论横幅) |
| 战略判断 | 大字 + 卡片矩阵 |
| 指标 / 量化证据 | 指标卡 + 公式 / 提醒带 |
| 量化规模(几个头条数字) | `statBand`(大数字 + 分隔 + 备注) |
| 产品能力 | 系统图 + 能力引注 |
| 路线图 / 交付 | 时间线 + 里程碑 + 风险 |
| 风险 / 缺口 | 热力图、优先级堆叠、红色高亮 |

## 图形路线选择

上面的决策树选择页面关系。`VISUAL-SELECTION.md` 选择生产路线。画之前两者都做。

路线顺序:

1. **组件库**——先用 `COMPONENT-CATALOG.md` 和框架的 `components/`。一个能被 `stateFlow`、`workflowConfig`、`pipelineFlow`、`featureGrid`、`hubSpokeCapability`、`capabilityMatrix`、`topology` 或另一个现有原型表达的页面,不应重画成松散的盒子。
2. **外部图形**——当素材是证据、或重画耗时太长时,用已有 PPT 图形、截图、产品图片、地图、GIS/3D 渲染或源图示。
3. **image2 / imageSlot**——为矢量画起来会很粗糙的场景、产品、写实或隐喻图像预留一个槽位;产出 `IMAGE-ASSETS.md` 的 prompt 规格。
4. **页面专属自定义**——只有在前三条路线被评估并记录之后才允许。

关系快捷方式:

- 状态、记忆、生命周期、"一个页面文件夹有本地记忆" -> 在自定义之前先试 `stateFlow`、`workflowConfig`、`goalPath` 或 `topology`。例如,一张"状态和记忆"页应展示状态转换和记忆锚点,而不是通用文本框。
- 工具系统 / 素材池 -> 试 `featureGrid`、`hubSpokeCapability`、`splitDossier`、`panelDuo` 或 `bulletColumns`;把 `imageSlot` 留给示例截图或生成的视觉样例。
- 流程 / 执行编排 -> 试 `processTimeline`、`pipelineFlow`、`milestoneTimeline`、`valueChain` 或 `workflowConfig`。
- 评审 / 评估 / gate -> 视页面是角色交接、生命周期、监控视图还是记分卡,试 `swimlaneProcess`、`stateFlow`、`dashboardMock` 或 `capabilityMatrix`。

线框是一种样式,不是一条路线。一张线框页仍然需要一个关系:流程、状态、层级、对比、工具箱、证据,或场景。

## 排版与布局规则

- 中文字体:`Microsoft YaHei` / `微软雅黑`。
- 英文和数字:可用时用 `Century Gothic`。
- 字号是一个**宽层级**,由共享的 `theme.type` 刻度驱动:标题/数字大(约 18–25pt),但支撑文字的大头——标签、说明、chip、表格单元、图内细节——真的小(约 6.5–10.5pt)。标准正文 ≈ 10.5pt,密集页 ≈ 9pt,微型标签 ≈ 7pt。每页用 ≥4 种不同尺寸;对比(而不是一致的大)才读作精致。
- 不要靠盲目缩小文字来解决拥挤的幻灯片。减少文字、拆分页面,或转成图示。
- 让所有内容留在安全区内。对 16:9 1920x1080 设计,用大约 `x=96..1824`、`y=80..980`。
- 让视觉中心感觉居中,除非页面刻意用左/右构图。
- 用填充做强调、数据面板、徽章和焦点块。用线条和留白做分隔和结构。不要习惯性地做全填充或全线条的页面。
- 图标必须承载含义:角色、动作、指标、状态、模块、风险或素材。不要只把图标当装饰。

## 颜色语义(Color Semantics)——颜色必须编码含义

这是一条硬规则。最常见的 AI 味缺陷是颜色被用作装饰:条目在颜色上不同,但颜色差异什么都不代表。审阅员必须拒绝它。

- **一切默认为一种结构色**(在 Leander Base 里:深藏青 `primary`)。同级条目——四个对等的价值、六个对等的指标、一个流程的连续阶段——全都用同一种颜色。当事物相同时,相同是对的。
- **把强调色(红)留给页面上那唯一最重要的元素**——那一个头条数字、那一个焦点层、那一个当前步骤、那一张你想让视线落上去的卡片。如果一切都被强调,就没有东西被强调。每页争取一个强调焦点。
- **语义色只映射固定含义**:绿 = 最好 / 正向 / 成功;琥珀 = 警告 / 注意;红 = 错误 / 阻塞 / 焦点强调。绝不把绿/琥珀/红用于一个不是成功/警告/错误的类别。
- **第二种色相(例如蓝)只允许用于真正的第二类别**,不是为了多样。如果你说不出第二种颜色*代表*什么,就删掉它、用结构色。
- **用颜色编码真实关系**:强调(焦点 vs 背景)、权重/递进(填充 vs 描边,一种色相的深 vs 浅)、状态(ok/warn/error)。不要像彩虹一样逐条轮换颜色。
- 发一张页面之前,对每一种不同的颜色问"这个颜色告诉受众什么?"如果答案是"它只是不同",它就 fail。

## 设计的留白 vs 空白

只有当留白支撑一个焦点时,它才成立。

设计的留白通常有:

- 一个大的关键词、数字或图片。
- 一句简短的解释。
- 一条清晰的分隔线或色条。
- 另一侧的支撑卡片、图示或证据。

空白通常有:

- 孤零零飘着的小字。
- 内容很少的稀疏卡片。
- 没有视觉层级。
- 没有解释页面的图示。

空白页必须重新设计。

### 填满正文,或让它居中(Fill The Body)

最常见的留白缺陷是一个内容块被钉在页面顶部,页脚上方留一大条死缺口。这读起来像 AI 生成。一个组件必须做到以下之一:

- **填满正文安全区**(大致是 header 下方的 `y≈210..950`),当页面本该信息密集时:给卡片和间距定尺寸,让构图触达下三分之一。只有当子要点、证据或提醒能改进理解时才加;不要仅为占空间而加内容。
- **或把整块垂直居中**,让上下边距大致相等。对称的呼吸感读作设计过;一个只在底部的大缺口读作 bug。
- **或围绕一个强词、数字、图片、引言或视觉关系保留刻意的留白**。把目的记录为聚焦、停顿、张力、高级的克制、图片强调,或章节的呼吸空间。

当一页真的只有几条短内容时,刻意地选择:如果受众需要就加真实实质、把这一组居中,或把页面变成一个设计过的低密度构图。不要把一薄行拉满顶部、其余留白。绝不用把字号放大到超过字号体系来解决空。

## 反 AI 视觉指纹

避免:

- 每页都是通用的标题 + 段落 + 三张卡片。
- 装饰性渐变斑块、无意义的背景饰物,或假的视觉复杂度。
- 不映射内容的随机图标。
- 内容很少的巨大圆角卡片。
- 用小字来掩盖薄弱结构。
- 假数据、假 logo,或没有来源/边界的说法。
- 在整份 deck 里过度使用一种布局。

## 通用输出规则(Universal Output Rules)

不可妥协,与主题无关。最常见的质量失败是系统性的,不是单页的。

### 颜色必须编码含义

颜色是一个语义通道,不是装饰。绝不为视觉多样而变换颜色。

- 一个结构默认色(Leander Base:藏青 `primary`)用于所有同级/对等元素。
- 把品牌强调色(Leander Base:Westwell 红)留给每页那唯一的焦点元素——至多一个。如果没有东西是焦点,就一个都不用。
- 第二种色相只用于真正的第二类别,绝不用于交替。
- 状态色承载固定含义:成功/最好 = 绿,警告 = 琥珀,错误/阻塞 = 红,中性/不活跃 = 灰。只用于这些。
- 测试:对每一处颜色差异,说出它编码什么(焦点、类别、顺序、状态、权重)。如果说不出,就让它们同色。
- 反模式:N 张对等卡片循环 强调/藏青/蓝。对等卡片 = 一种颜色。

### 卡片贴合内容;剩余空间变成对称边距

无意义的内部留白(半空的卡片、底部的死带)是头号 AI 味信号。

- 给卡片/面板按它的内容定尺寸;不要固定一个高高度、任由内容飘在顶部。
- 从条目/行数计算块高,再把块在正文里垂直居中,让剩余空间变成相等的上下呼吸。
- 对称边距 = 设计的留白(可以)。不对称的死空间 = 缺陷(重新设计)。
- 如果内容真的稀疏,先决定页面是需要更多证据、还是应当保持一张低密度聚焦页。只有在能改进信息时才丰富;否则移除空容器、把留白设计出来。
- **线框不是漏洞。** 把白填充换成线框/描边并不能解决"填满页面"——一个框拉在很少的内容上(顶部稀疏、底部无用空白),读起来一样有 AI 味。"贴合内容再居中"的规则对框和对填充卡片一样适用。
- **偏空页的两种被认可布局:**(a)背景底 + 线框分隔,或(b)一个文字区 + 一个图形区拆分。绝不把卡片/框拉满整页。(见 `editorial.js`。)

### 排版使用一套共享刻度

- 让每一个文字尺寸都从单一的**字号体系** token(`theme.type`:`hero/h1/h2/lead/h3/bodyLg/body/bodySm/cap/micro/tiny`)驱动,而不是随手的数字。同一角色(页面标题、卡片标题、正文、说明)在每一页用同一尺寸;密集页取更小一档,疏朗页取更大一档——和谐来自共享刻度,而不是逐页猜。
- **校准到 cactus 参考 deck(实测 `sz` 值):章节/卡片标题约 20–22pt、lead 约 15–18pt、标准正文约 10.5pt、密集正文约 9pt,而**大多数**文字——图内标签、chip、表格单元——是 6.5–7.5pt。**(design-px = pt×2,`pxPerPt:2`,所以正文 = 21px → 10.5pt。)让每一个尺寸都从 `theme.type`(`hero/h1/h2/lead/h3/bodyLg/body/bodySm/cap/micro/tiny`)驱动;绝不硬编随手的磅数。
- **不要靠"把一切顶到一个尺寸"来"修小字"**——那会压平层级、让支撑文字看着过大/丑("小字太大了实在太丑")。细节标签*本该*小(6.5–9pt);要拒绝的是对其角色不可读、或与其容器不成比例的文字,而不是小本身。当用户为"字体感觉小/精致"援引一份参考时,打开它、读真实的 `sz` 值,而不是猜——大标题 + 大量融合的小细节才读作精致。
- **副标题是页面的一句话论点**——它概括核心结论,绝不是标题的口语化复述。

### 视觉形态随故事变化

- 当重复制造了刻意的节奏、对比或呼应时,允许重复。只有当页面有不同的叙事任务、却被硬塞进同一版面结构、且没有 `echoWith` 和理由时,复用一个组件才成为缺陷。
- 避免"每页 = 一个盒子里塞文字"。从当前项目的需求里选择表达形式:线框结构、大型图解隐喻、证据截图、图片主导页、大字号、图表、图示,或克制的卡片。没有通用的图片/页面配额。
- 不要继承上一份 deck 的页面顺序、视觉特征或组件配比。每一次都从当前 brief、源素材、主题和已审批蓝图出发。

### 每一页都建立主题底

- 每张内容页都设置主题背景;绝不依赖默认白。背景与封面/章节页不同的页面是一个缺陷。

### 品牌 chrome 单一来源

- Logo 尺寸/位置是主题 token 里的一个标准值,在封面、内容和封底上完全相同地应用。绝不逐页手设 logo 尺寸。匹配源模板(Leander Base 在 1920 画布上约 90px 宽)。

## 标杆样张规则

在整片生产之前,创建 2-3 张真实可编辑的 PPTX 样张:

1. 封面或定调页。
2. 一张普通的高密度内容页。
3. 最复杂的图示或机制页。

样张必须好到能让用户判断最终质量。不要做一个线框然后管它叫样张。

## 页面隔离规则

一张幻灯片是最小的设计和修复单位。

- 给每一页一个来自 `outline.md` 的稳定 `Page ID`。
- 把页面专属的布局逻辑集中在一个命名的幻灯片函数、或清楚标注的幻灯片块里。
- 对重复模式用可复用组件,但不要把页面专属内容藏进全局主题文件里。
- 如果反馈影响一页,只修那一页,除非缺陷来自一个共享组件。
- 如果反馈影响一个重复组件,修组件,并重渲染每个用到它的页面。
- 做视觉修复时不要改动页面顺序、章节结构或说法,除非用户批准。

## 自检

对每一张标杆页、以及每一批终版幻灯片之后运行。

- [ ] 页面 ID 和页号匹配 `outline.md`。
- [ ] 页面有一个清晰的 takeaway。
- [ ] `page.json.visualSelection` 存在,并解释为什么选定路线胜过组件库/外部/image2 备选。
- [ ] 页面有真实的图示或视觉解释,不只是文字卡片。
